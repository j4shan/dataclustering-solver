The abstract model has two moves: resolve a predicate to containers, then read every event in each activated container. Spark and Delta Lake make those moves concrete through metadata pruning, file assignment, and workload evidence. These three diagrams show where each piece attaches — and where the production mapping remains incomplete.

The engine diagrams locate the implementation seams. The appendix below returns to the storage model itself and holds one twelve-event instance still, so each figure can isolate a single relationship: stored rows, index resolution, event support, then whole-container activation. It is a teaching instance, not a benchmark of Spark or Delta Lake.

The index table stores one narrow row per event: features, container_id, and record_id. A query scans those features, evaluates its predicate, and collects the container_id values of matching rows; those are the containers to open. Under Spark, container_id is realized as a partition — Hive-style PARTITIONED BY values on the files. Dynamic partition pruning applies a runtime filter, often from the small side of a join, to those partition values so unmatched partitions are never scanned.
