Once container assignment is exercised, the solution can be deployed to a production data lake such as Databricks. This page takes knowledge already on Problem Statement, Measuring Data Layout Fitness, and Drawing Storage Boundary and maps it onto a Lakehouse write path and a Spark read path. The figure The go-live process is six numbered actions, one per section below.

1. Collect a target sample

A sample of the target dataset is collected together with fetch query statistics for that sample. A preliminary analysis on that pair quantifies how much data skipping the workload can expose and the cost saving that skipping would represent.

That analysis is a screening estimate on the sample. The benchmark harness remains the surface that reports exact workload replay.

2. Identify split decision trees

The techniques taught in Measuring Data Layout Fitness grow split decision trees from training samples. The search starts with a cost-effective algorithm: the cheap greedy top-down baseline named there. Business insight then narrows the remaining search space to the columns, grains, and predicates a practitioner already treats as load-bearing.

3. Estimate leaf skipping potential

Apply the Multiple-Choice Knapsack Problem (MCKP) taught in Drawing Storage Boundary to the leaf nodes of the trees from §2, and report an estimated data-skipping potential on every leaf, the static leaf benefit of that page.

4. Inspect the holdout

The split decision trees from §2 and a container assignment strategy are applied to holdout samples. The assignment strategy may be the MCKP allocation from §3 or a simple fixed-capacity assignment (every leaf packed at one shared container size).

Inspect the estimated weighted-average data skipping ratio on the holdout to check that the training tree transfers.

5. Implement data ingestion

The abstract layout maps onto the write path of a Databricks Lakehouse. The figure Ingestion writes two tables is the fan-out.

process concept Databricks realization
split decision a grouping or a predicate
container assignment Delta Lake partition assignment (partition_id)
feature index an independent narrow Delta table
events a wide Delta event table

On each arriving batch (a micro-batch when the stream is incremental), Spark applies a group-by expression built from the custom layout decision tree in §2. That cut divides the batch into logical groupings. The brand-sales example groups by brand_id and pricing_tier.

Ingest splits every grouping into approximately fixed-size containers (Delta partitions). Container capacity is T. Size is approximate because hash collisions are accepted.

A stateful assignment tracker is a dedicated table with one row per logical grouping.

term symbol meaning
grouping identity key — the grouping the tree produced
container sequence number k monotonic per grouping, starting at 1
filled count s_1 records already in the one partial container
container capacity T target records per container
batch size N records in this batch for that grouping
virtual slot V the hashed address in [s_1, s_1 + N)

A grouping has only one partially filled container. Every earlier container in that grouping is full. A partition is identified by its grouping key and its sequence number.

The job maps the batch onto virtual slots, then reads a sequence number from the slot. Let the tracker's current sequence be k and its filled count be s_1 (s_1 < T). For each record:

V = s_1 + pmod(xxhash64(identity), N)
seq = k + floor(V / T)

Identity is the record identity columns. xxhash64 and pmod are the Spark SQL functions. Two records may share a V; that collision is accepted, so a container's achieved size may miss T.

The grouped, assigned stream is written to two destinations:

  • a narrow index table of query-predicate features plus partition_id;
  • a wide event table of the full attributes plus partition_id plus record_id.

The index written here has no record_id and no non-predicate attribute, because the §6 prescan only collects partition_id values.

6. Implement query optimization

Container-skipping maps onto the read path. The figure Spark DPP skips from the index is the worked example: it uses the same brand-sales index that §5 wrote.

process concept Databricks realization
container-skipping an index-table prescan plus Spark Dynamic Partition Pruning (DPP)

A multi-select query prescans the narrow index and computes the set of matching partition_id values. Spark Dynamic Partition Pruning broadcasts that set to each Databricks worker as a metadata filter. Each worker trims its cloud-object download targets to the activated partitions. Activation stays at partition grain.
