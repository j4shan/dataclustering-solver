After the container assignment has been evaluated, the design can move to a production data lake such as Databricks. This page maps the ideas from Problem Statement, Measuring Data Layout Fitness, and Drawing Storage Boundary to the Lakehouse write path and Spark read path. Deployment Process Flow shows the planning path.

1. Collect query usage statistics

The query-path collector in §6 writes usage_summary. In this wide usage-statistics table, each query–row cell records a boolean flag: whether that query selected that row. It represents the same history as the two-column selection log. Figure 3 shows the collector writing the store; Figure 1 reads it.

Databricks system.query.history records predicates rather than selected rows. The usage table therefore needs replay, instrumentation, or sampling. Binning the per-instance flags by minute, hour, or date makes the table smaller but loses resolution.

The resulting analysis is a screening estimate; the benchmark harness reports exact workload replay.

2. Optimize split decision trees

Use training samples to grow split decision trees with the techniques in Measuring Data Layout Fitness. A resource monitor and complexity bound limit the search. Keep a beam of candidate trees so holdout can compare several alternatives.

Delta Lake and Iceberg cannot hold hundreds of millions of table partitions. Since every leaf needs at least one partition, the table’s partition limit must also govern when the search stops or prunes a tree.

If the holdout check in §4 fails, it records heuristics for the unqualified split conditions: cuts or predicates that did not transfer. The next search pass reads those heuristics and omits those conditions. The inner cycle of listing cuts, scoring them, and replacing a leaf remains in Measuring Data Layout Fitness.

3. Optimistic knapsack simulation

For each beam candidate from §2, run the Multiple-Choice Knapsack Problem (MCKP) from Drawing Storage Boundary. Use the Delta Lake table-partition limit as the global container budget.

Each candidate starts with one container per leaf. As MCKP spends the remaining budget, it reports the estimated skipping ratio and marginal efficiency at each iteration.

A chart can extend a logarithmic container-count axis beyond the table limit to compare metadata overhead with skipping performance. It also shows what finer storage granularity might buy. The overlay may appear on Figure 1 beside the MCKP spend node.

Keep ingestion time—minute, hour, day, or month—in the bottom split layer. Age commonly tracks usage frequency, so the final cut should preserve that time grain at the leaf.

4. Experiment simplified assignment on holdout

MCKP estimates maximum potential from a static dataset, but marginal-efficiency rankings learned on training data can change substantially on a forward stream. For the holdout check, apply the beam from §2 with a simpler assignment: ignore those rankings and use one global equal-size container policy.

Use observed compressed record size to set container capacity. The resulting files are fragmented micro-partitions—for example, at least 8 MB on AWS S3—while remaining within the global table-partition overhead.

Check the estimated weighted-average data-skipping ratio on the holdout to see whether a training tree transfers. Holdout acts as a gate: a tree that passes is frozen for ingest; a tree that fails records the unqualified-split heuristics from §2 and returns to search.

5. Deploy container assignment during Ingestion

On the Databricks Lakehouse write path, the layout moves through a landing table, a specialized writer, and a fan-out. Ingestion Time Integration shows those stages.

Spark Structured Streaming / Auto Loader and a stream writer persist the transient brand-sales stream in streaming_sink. This landing table holds each arriving batch as it comes.

A CRON scheduler first runs the consistency checker. The checker reads a custom checkpoint table whose write-ahead log makes the multi-table fan-out idempotent; Delta Lake has no such log for this fan-out. It may clean partial ingest state before launching the specialized writer.

The specialized writer then processes the landed batch. Its splitter reads streaming_sink and the frozen tree from §4; the allocator reads tracker state and finalizes partition_id. A fan-out writes the narrow index, tracker, and partitioned_sink, then appends a WAL commit.

schema Databricks realization
split decision a grouping or a predicate
container assignment Delta Lake partition assignment (partition_id)
feature index and events a narrow Delta table and a wide Delta event table (partitioned_sink)

For each arriving batch, Spark applies a conditional group-by expression from the custom layout decision tree in §2. An incremental stream supplies these as micro-batches. The expression divides records into logical groups, by brand_id and pricing_tier in the brand-sales example.

A dedicated stateful assignment tracker table keeps one row and a container-fill count per logical group. The job uses that state to assign partition_id without a partition-sort. The bucket-hash-assign remains approximate because collisions are accepted.

term symbol meaning
grouping identity key — the grouping the tree produced
container sequence number k monotonic per grouping, starting at 1
filled count s_1 records already in the one partial container
container capacity T target records per container
batch size N records in this batch for that grouping
virtual slot V the hashed address in [s_1, s_1 + N)

The tracker models each logical group with one active partial container and treats all earlier containers as full. A grouping key and sequence number identify each partition.

The job first maps batch records to virtual slots, then derives each slot’s container sequence number. Let the tracker hold current sequence k and filled count s_1 (s_1 < T). For each record:

V = s_1 + pmod(xxhash64(identity), N)
seq = k + floor(V / T)

The identity input comprises the record’s identity columns; xxhash64 and pmod are Spark SQL functions. Two records can receive the same V. The accepted collision means a container’s achieved size may differ from T.

After assignment, the stream goes to two destinations:

  • a narrow index table of query-predicate features plus partition_id;
  • a wide event table (partitioned_sink) of the full attributes plus partition_id plus record_id.

The narrow index excludes record_id and all non-predicate attributes. The §6 prescan collects only partition_id values from its matching rows.

Continuous ingest creates new, fragmented files in a micro-partition layout. Without consolidation, tens of millions of small files can overwhelm catalog metadata. Section 7 describes the maintenance path.

6. Activate data skipping optimization

At query time, container skipping follows the read path: index scan, driver activation, worker fetch, durable result, and usage collection. Query Time Integration traces that path.

Spark Dynamic Partition Pruning (DPP) supplies granular container skipping. A multi-select query prescans the narrow index for matching partition_id values. DPP broadcasts that set to Databricks workers as a metadata filter, so each worker fetches only activated containers from partitioned_sink, the event table. Workers write a durable query result; the usage collector reads it and persists aggregated usage_summary.

For this deployment, DPP over millions of internal partition-metadata records calls for a large driver, such as an AWS rgd series instance with at least 256 GB. The adaptive query planner also needs a high broadcast threshold—256 MB, for example—to inject a broadcast partition filter into the target table scan. Spark config: autoBroadcastJoinThreshold names that threshold. Activation remains at partition grain.

7. Hybrid table architecture and continuous consolidation

streaming_sink holds the landing copy; partitioned_sink holds the containerized event store downstream.

The CRON scheduler also runs an optimizer. It reads and rewrites partitioned_sink so each partition stays in one file, leaving Z-order off and the fan-out to the specialized writer.

A single whole-table OPTIMIZE commit is prone to concurrency failures in this workflow. Instead, bucket millions of partitions into disjoint tasks. They can optimize in parallel, each committing its own non-conflicting transaction.

For streaming ingest, use ingestion time as a split dimension. The landing tier accepts the high-frequency stream as landed rows; applying the tree-split layout there would worsen small-file fragmentation. The specialized writer copies rows from landing periodically, at a pace that can tolerate granular containerization. Recent rows remain in the unoptimized tier, concentrating maintenance where skipping coverage is worth the cost.

Rows with one schema can still use complementary storage layouts. Different engines or hardware can support those layouts behind one user-facing table.
