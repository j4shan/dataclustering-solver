Once container assignment is exercised, the solution can be deployed to a production data lake such as Databricks. This page takes knowledge already on Problem Statement, Measuring Data Layout Fitness, and Drawing Storage Boundary and maps it onto a Lakehouse write path and a Spark read path. The figure Deployment Process Flow draws that planning path.

1. Collect query usage statistics

Persist usage_summary, a usage-statistics table. Each cell is a boolean flag for one query and one row: whether that query selected that row. The table is the wide boolean view of the same history as the two-column selection log. The usage statistics collector on the query path in §6 writes this store. Figure 3 draws that write; Figure 1 reads the same named store.

Databricks system.query.history records predicates, not selected rows, so construct the table by replay, instrumentation, or sampling. Aggregating those per-instance flags into minute, hour, or date bins shrinks the table and loses resolution.

That analysis is a screening estimate. The benchmark harness reports exact workload replay.

2. Optimize split decision trees

Grow split decision trees from training samples with the techniques in Measuring Data Layout Fitness. Run the search under a resource monitor and a complexity bound. Keep a beam of candidates so holdout sees several competing trees.

Delta Lake and Iceberg cannot host hundreds of millions of table partitions. Each leaf occupies at least one table partition, so project the table's partition limit onto the search stop and prune tests.

When holdout in §4 fails, the fail path writes heuristics of the unqualified split conditions: the cuts or predicates that did not transfer. Search then reads those heuristics and omits those conditions on the next pass. The inner list, score, and replace cycle stays on Measuring Data Layout Fitness.

3. Optimistic knapsack simulation

Apply the Multiple-Choice Knapsack Problem (MCKP) from Drawing Storage Boundary. Set the Delta Lake table partition limit as the global container budget. Run MCKP on every beam candidate from §2.

MCKP starts at one container per leaf and spends the budget piecemeal. Estimated skipping ratio and marginal efficiency appear at each iteration.

An overlay chart on a log container-count axis that continues past the limit compares table metadata overhead with skipping performance and shows what a more granular store could still buy. That overlay may sit on Figure 1 as a panel on the MCKP spend node.

Keep an ingestion-time dimension (minute, hour, day, or month) in the bottom split layer. Age commonly tracks usage frequency, so the last cut should leave that grain on the leaf.

4. Experiment simplified assignment on holdout

MCKP is a maximum-potential analysis on a static dataset. Relative marginal-efficiency ranking on training can move a long way on a forward stream. Apply the beam from §2 and a simplified assignment that ignores the ranking and enforces one global equal-size container policy.

Set container capacity from the observed compressed record size so the files are fragmented micro-partitions (for example at least 8 MB on AWS S3), still inside the global table-partition overhead.

Inspect the estimated weighted-average data skipping ratio on the holdout. That quantity is the check that a training tree transfers. Holdout is a gate: a tree that transfers freezes for ingest; a tree that fails writes the unqualified-split heuristics of §2 and returns to search.

5. Deploy container assignment during Ingestion

Map the layout onto the write path of a Databricks Lakehouse. The figure Ingestion Time Integration shows the landing path, the writer assembly, and the fan-out.

Spark Structured Streaming / Auto Loader and a stream writer persist a transient brand-sales stream into streaming_sink. That landing table stores arriving batches as they come.

One CRON scheduler fires a consistency checker. The checker reads a custom checkpoint table that records a write-ahead log so a multi-table write can be idempotent. Delta Lake has no such log for this fan-out. The checker may clean partial ingest state, then launches the specialized writer.

The specialized writer is one assembly line. A data splitter reads streaming_sink and the frozen tree from §4. A container allocator reads the tracker and finalizes partition_id. A fan-out writes the narrow index, the tracker, and partitioned_sink, then appends a WAL commit.

schema Databricks realization
split decision a grouping or a predicate
container assignment Delta Lake partition assignment (partition_id)
feature index and events a narrow Delta table and a wide Delta event table (partitioned_sink)

On each arriving batch (a micro-batch when the stream is incremental), Spark applies a conditional group-by expression built from the custom layout decision tree in §2. That cut divides the batch into logical groupings. The brand-sales example groups by brand_id and pricing_tier.

A stateful assignment tracker is a dedicated table with one row per logical grouping. It records container fill so the job can assign partition_id without a partition-sort. The bucket-hash-assign is an approximation: collisions are accepted.

term symbol meaning
grouping identity key — the grouping the tree produced
container sequence number k monotonic per grouping, starting at 1
filled count s_1 records already in the one partial container
container capacity T target records per container
batch size N records in this batch for that grouping
virtual slot V the hashed address in [s_1, s_1 + N)

A grouping has only one partially filled container. Every earlier container in that grouping is full. A partition is identified by its grouping key and its sequence number.

The job maps the batch onto virtual slots, then reads a sequence number from the slot. Let the tracker's current sequence be k and its filled count be s_1 (s_1 < T). For each record:

V = s_1 + pmod(xxhash64(identity), N)
seq = k + floor(V / T)

Identity is the record identity columns. xxhash64 and pmod are the Spark SQL functions. Two records may share a V; that collision is accepted, so a container's achieved size may miss T.

The grouped, assigned stream is written to two destinations:

  • a narrow index table of query-predicate features plus partition_id;
  • a wide event table (partitioned_sink) of the full attributes plus partition_id plus record_id.

The index written here has no record_id and no non-predicate attribute, because the §6 prescan only collects partition_id values.

Continuous ingest into a micro-partition layout creates fragmented new file objects. Left unattended, tens of millions of small files overwhelm the catalog metadata system. §7 states the detailed solution.

6. Activate data skipping optimization

Container-skipping maps onto the read path. The figure Query Time Integration follows that path: index scan, driver activation, worker fetch, durable output, then the usage collector.

Spark Dynamic Partition Pruning (DPP) is Spark's out-of-the-box mechanism for granular container skipping. A multi-select query prescans the narrow index and computes the set of matching partition_id values. Spark DPP broadcasts that set to each Databricks worker as a metadata filter. Each worker fetches only the activated containers from partitioned_sink (the event table) and writes a durable query result. The usage statistics collector reads that result and persists aggregated usage_summary.

DPP over millions of internal partition-metadata records needs a large driver node, for example an AWS rgd series instance with at least 256 GB. The adaptive query planner also needs a high broadcast threshold, for example 256 MB, so it can inject a broadcast partition filter into the target table scan. Spark config: autoBroadcastJoinThreshold is that threshold. Activation stays at partition grain.

7. Hybrid table architecture and continuous consolidation

streaming_sink is the landing copy. partitioned_sink is the containerized event store downstream of that landing.

The same CRON that fires the consistency checker also fires an optimizer. The optimizer reads partitioned_sink and writes it back so each partition stays one file, with Z-order left off and the fan-out left to the writer.

Do not run one OPTIMIZE over the whole table as a single Delta transaction; that commit is prone to concurrency failures. Bucket millions of partitions into tasks so disjoint subsets optimize in parallel and each subset commits on its own, non-conflicting transaction.

For streaming ingest, split on ingestion time. The landing tier takes the high-frequency stream as landed rows; a tree-split layout there makes small-file fragmentation worse. The specialized writer periodically copies from the landing at a frequency that can tolerate granular containerization. Recent rows stay in the unoptimized tier, so maintenance is spent where skipping coverage is worth it.

Rows that share a schema need not share one storage strategy. Complementary layouts, and different engines or hardware under them, can sit behind one user-facing table.
